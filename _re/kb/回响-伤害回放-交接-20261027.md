## 7. 今天踩的坑（完整清单，按损失排序）

### 7.1 把游戏卡死两次（最贵）

**写法**：在 UI 按钮回调里做全表遍历——

```cpp
FindNameIdByPath("/Script/HTGame.HTAbilityCharacter");  // FName 全表，秒级
g_ue.FindClassById(id);                                 // GObjects，秒级
FindFuncByName(ch_cls, "OnDamaged");                    // 只查直接 Children
```

**现象**：点按钮后游戏无响应，只能强杀。
**正确做法**：用分帧扫描（`ProbeScanStep` / `Level->Actors`），或从已知对象直接取 UClass（`actor + 0x10`），再沿 `SuperStruct@0x40` 上溯。
**教训**：**只读 ≠ 便宜**。我当时以"只读不调用所以安全"为由跳过了分帧，这是判断错误。

### 7.2 三道插件加载门槛（每道都浪费了一轮）

| 报错 | 原因 | 解法 |
| --- | --- | --- |
| `unknown-capability capability=ue5-functions` | manifest 声明了这版 Core 不认识的能力 | 删掉该能力声明 |
| `code=static-crt`（`RtlPcToFileHeader` 导入） | 用了默认静态 CRT | 加 `/MD` |
| `code=missing-cxx-throw-bridge` | C++ 插件必须导出异常桥 | 编入 `sdk/cpp/plugin_cxx_throw_bridge.cpp` |

排查入口：`Anomaly\logs\anomaly-runtime.jsonl`，筛 `component=plugin-manager`。

### 7.3 `ufn=0`：`FindFuncByName` 只查直接 Children

蓝图类（`player_036_zankou_C`）上查不到 `OnDamaged`，它声明在祖先 `AHTAbilityCharacter` 上。
**解法**：沿 `UStruct::SuperStruct`（`+0x40`）上溯，最多 8 级。实测 `depth=3` 命中。

### 7.4 `od: call` 静默不执行

条件里写了 `g_pe_addr != 0`，而那个全局只有装了 PE 钩子才有值 → 整段被跳过，日志里连行都没有。
**解法**：用 `base + 0x3E41360`（`ApplyGEDirect` 里已在用的同一算式）直接取 ProcessEvent。
**教训**：探针的"没输出"要先怀疑条件不成立，不要先怀疑逻辑。

### 7.5 HP 读成 0：读错对象

`asc + 0x1A38` 是 **ASC** 的 HP 偏移；在角色 actor 上读得到 `0.0` 且 `SafeF32` 仍返回成功，**不会报错**，极易误判成"HP 为 0"。

### 7.6 `FBufferData` 比 Dumper 列出的字段多 8 字节

按字段算到 `nStartTime`(0x48) 结束只有 0x50，实际结构是 0x58 → `static_assert` 直接失败。
**解法**：补 `pad50[8]`，并把 `static_assert(sizeof(FBufData) == 0x58)` 留在代码里当护栏。

### 7.7 记录里的原生 RVA 不可用

`dump-5.6.1.md` 记的 `K2_ApplyGameplayEffectToTargetWithClass → 0x7778E50`，运行时按名解析到的却是完全不同的地址（另一个 build）。
**结论**：只能运行时按名字解析，**不要用文档里的 RVA 直接 call**。

### 7.8 新增插件目录必须重启游戏

宿主在启动时建立插件 catalog，运行中新增目录不会被发现（界面点启用必然失败）。
但**替换已有插件目录里的 `plugin.dll` 是热重载**，不用重启。

### 7.9 编码类误判（宿主侧，附带记一下）

- 用 `Encoding.ASCII` 去匹配 Core 里的中文字符串必定假阴性，**中文判据必须用 UTF-8**；
- `Start-Process` 在本机会因环境块里 `http_proxy`/`HTTP_PROXY` 大小写重复而抛异常，用 `&` 直接执行或先清空代理变量。

`FFrame::Locals = 0x20` **不是猜的**：部署 Profile `Anomaly\profiles\nte\nte-current.json` 里

### 11.2 踩到的新坑：**在 PE 订阅回调里调用宿主服务会把游戏卡死**

第一版把 `DecodeName`/日志直接放在订阅回调里。激活订阅后（18:19:26，generation 8）游戏立刻
不再出帧：窗口 `Responding=False`、4 秒两次全屏截图逐像素相同、进程 CPU 仅 ~6%（各线程全在
Wait）→ 不是忙等，是死锁。
高度可疑点：`anomaly.ue5.names::resolve_utf8` 在宿主侧是 `State::ResolveNameId` →
`std::scoped_lock lock(mutex)`，而订阅回调是在 Game 线程 `original ProcessEvent` 之前派发的
（`services/ue5.h` 契约）。宿主自己的 Pre 路径刻意用 `*Locked` 无锁变体，正是因为这条路上不能拿锁。

**规矩（下一轮别破）**：PE 订阅回调 / exec thunk detour 里只做「指针比较 + memcpy」，

### 11.4 第一条实测结论：**游戏不走那 8 个 Apply\* UFunction**（硬否证）

   调了什么」的直接证据，且解析在 UI 线程做，不会像 11.2 那样锁死。
2. **8 路 exec thunk 剥离**：把 8 个 Apply\* UFunction 的 `+0xD8` exec thunk 全挂上（`anomaly.interop.hook`，
   宿主按 generation 管理、卸载自动回收）。只有 `K2_ApplyGameplayEffectToTargetWithClass` 抄 0x78 参数，
   其余 7 个只计数；任一路径第一次被调用会打印 `thunk[i]: FIRST call n=.. fn=..`。
   这是对「蓝图直调 exec thunk、绕过 ProcessEvent」的针对性检验。

1. **触发**：宿主伤害事件流（`anomaly.nte.combat::next_damage_event`），只在 UI 线程轮询；
2. **GE 来源**：受害方 ASC 的 **`LastDamageGEDef` @0x2378** → 取它的 UClass（`def+0x10`）

3. **施加**：`MakeEffectContext()`（0x18 返回）+ `BP_ApplyGameplayEffectToTarget(

4. **验证**：伤害是**异步到账**的（当次调用 `d=0`、`h=FFFFFFFF` 都属正常），
   所以用「上一发之后的 HP − 这一发之前的 HP」归因，即日志里的 `async=`。

**踩过的四条锁死/坑（都已在代码里注释）**

- 游戏线程回调域里**绝不能**调 `DecodeName`（宿主 `State::mutex`）→ UFunction 解析放 UI 线程；
- `on_update` 虽是 Game 线程，但**不能**在那里发 ProcessEvent；
- UI 线程（`on_draw`）也不是 Game 线程，发 ProcessEvent 必须先转交给订阅回调域；
- 自动回放要防自喂：自己的施加也会产生伤害事件 → `g_ge_last_apply_ms` 1200ms 抑制窗口。

### 12.5 速率（2026-10-27 23:10，commit `b6d305d1`）

实测发现旧引擎**每帧最多施加 1 发**，所以实际速率被 UI 帧率限制在 ~46 发/秒：
